The same LIKE bug in five local-first databases

A field report on client-side query correctness — with a 10-second test for your own engine.

Local-first and sync engines all share one hard problem: the client has to re-evaluate queries against its local copy of the data (for optimistic updates, offline reads, and reactive subscriptions), and that client-side evaluation has to agree with whatever the server / SQLite / Postgres would have returned. The moment the two disagree you get silent wrong results — a row appears locally that the server would never return, or vice-versa. For a database that's the worst class of bug: no error, no crash, just quietly incorrect data.

I audited how several popular local-first / query engines implement one tiny, ubiquitous operator — SQL LIKE — in their client-side matcher. Five of them got it wrong, in the same family of ways. All five now have fixes proposed:

The pattern

SQL LIKE is deceptively simple: % matches any run of characters, _ matches exactly one, everything else is a literal, and — crucially — the wildcards match any character, including newlines. The whole value must match. The usual implementation compiles the pattern to a regex:

// the tempting version
const re = new RegExp('^' + pattern.replace(/%/g, '.*').replace(/_/g, '.') + '$')

This has three independent bugs, and the five projects each hit one or more:

  1. No dotall. In JS regexes, . doesn't match \n without the s flag, so %→.* and _→. stop at a newline. 'a\nb' LIKE 'a%b' returns false; every SQL database returns true.
  2. No metacharacter escaping. Unescaped, characters like ., +, (, [ are treated as regex. LIKE 'a.b' matches 'axb', and LIKE 'a(b' throws Invalid regular expression.
  3. Wrong anchor flag. The m (multiline) flag makes ^/$ match interior line boundaries, so 'fooa\nbar' LIKE 'foo_' returns true for an 8-character value. (SQLite: false.)

A portable test

You can check your own engine in ten seconds. The correct mapping escapes metacharacters, keeps %/_ as wildcards, anchors to the whole string, and uses dotall:

function likeToRegExp(pattern, caseInsensitive = false) {
  const escaped = pattern.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')
  const body = escaped.replace(/%/g, '.*').replace(/_/g, '.')
  return new RegExp('^' + body + '$', caseInsensitive ? 'is' : 's')
}

And the cases that catch the bugs (all should match a real SQL LIKE):

'a\nb'    LIKE 'a%b'   => true     // % spans newlines
'a\nb'    LIKE 'a_b'   => true     // _ matches a newline
'ab\n'    LIKE 'ab'    => false    // whole value must match
'fooa\nb' LIKE 'foo_'  => false    // no interior-line matching
'a.b'     LIKE 'a.b'   => true     // dot is a literal
'axb'     LIKE 'a.b'   => false    // …not "any char"
'a(b'     LIKE 'a(b'   => true     // and must not throw

If your client-side matcher disagrees with your server on any of these, you have silently-wrong query results in production.
